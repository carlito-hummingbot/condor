Build: From Idea to Live Bot

Status: in review, built in the showcase only · Shell and the five stages exist as patches; the rail rename round covers the door · Last updated: 2026-11-28

The third door stops being a shelf of four loose tools. It becomes one path a trader walks with a single bot: design it, backtest it, dry-run it, send it live, then improve it. Every stage hands a finished draft to the next, and every stage answers one question.

Why

Today the third door is called Labs and it holds four tools: Design, Backtest, Test Run and Diagnose. Nothing says which one comes first, what "done" looks like, or what a person who has an idea is supposed to do with it. A trader arrives with "I want to quote this pair", sees a toolbox, and has to invent the order themselves.

Turning an idea into a live bot is one journey, not four tools: decide what to build, test it on history, watch it on live data without money, send it live with limits, then make it better from what actually happened. Each of those steps answers a single question and produces a finished draft for the next one, so the page should read as one guided path with five stages, and the stage you are in should be obvious from the moment the page opens.

The name should be a verb, next to Explore. Explore is for finding something to run; Build is for making it live. Build also names what the page produces, a bot that trades, rather than the tools used inside it.

The five stages

Five stages, in this order: Design (what are we building?), Backtest (did it work on this data, after costs?), Dry Run (does it still work on live data with no orders sent?), Deploy (what are the limits, and is it really meant to go live?), Improve (what did it do, and what should change?). The numbered stepper carries the stage, and the tab row under it does the same job with a shorter label; both are shown here on purpose (see the notes).

1. Design — the guide, then the assistant

Flow. Nine answers, then a conversation. The form is short on purpose: each answer is one click or one field, and the right-hand card fills in as you go, so the draft is visible the whole time. Start designing asks the assistant to reflect the answers back in one paragraph and to ask the next question that matters; from there the design is refined in chat until the trader marks it done. The guide stays one click away (Edit guide), so a wrong answer is never a dead end.

The fields. The same ten answers appear in the draft contract, the Design guide and the Backtest and Deploy summaries, so nothing has to be re-entered later.

2. Backtest — one run, one question

Flow. Confirm what is being tested, run it, read the verdict. The run is stated in one line (range, interval, starting capital) so a result can never be mistaken for a different setup. The results lead with the six figures a trader judges first — net return, max drawdown, win rate, Sharpe, trades, fees — then the equity line against buy-and-hold, because a strategy that loses to holding the coin has not earned a deploy.

3. Dry Run — the backtest meets a clock

Flow. Start a paper session against the live book, then compare it with the backtest side by side. Nothing is sent to an exchange. The table deliberately compares shape rather than size, since an hour of paper cannot earn ninety days of return, and it says so under each row. A readiness list below decides whether Deploy should be opened at all.

4. Deploy — pre-flight, limits, then one confirmation

Flow. A pre-flight list, a risk and capital form, a review card, then a typed confirmation. Deploy is the only stage that can move money, so it is the only stage with a second gate: the operator types the bot title or the word DEPLOY, and the dialog repeats any check that is still open before it will continue. The picture below is the state after that gate: the bot is live.

5. Improve — read, suggest, iterate

Flow. Compare, diagnose, decide, version. Live results are read against the backtest and the dry run with signed deltas, so a trader can see where reality beat or missed the prediction. Health cards cover the operational questions (fill rate, latency, errors, uptime, inventory skew). Each suggestion carries its reason, expected impact and risk, and can be accepted, dismissed or sent back to Backtest. Create v2 draft keeps v1 live and opens Design with the flags reset.

Continuity: one bot, many doors

A bot is not built in one sitting, and it does not belong to one page. A trader meets it in Explore, watches it on the Dashboard, and comes back to it a week later. So the draft is carried between pages, and each entry point says where the bot came from.

The draft survives a refresh, and the header says so. Opening Build with work in progress offers Continue where you left off with Resume, Start new or Discard, and a link that meets an existing draft asks whether to replace it or keep both. My drafts keeps the last few.

Stage guards are gentle. Opening Deploy before a backtest or a dry run shows a notice with Go to Backtest and Continue anyway. Nothing is locked, because the operator may know what they are doing — but nothing is silent either.

Approve Build as the name of the third door, and the five-stage path (Design, Backtest, Dry Run, Deploy, Improve) with one picture per stage. Two things are for review only: the two tab rows, and the wording of the name itself. The page is sample data throughout: no bot is created, backtested or deployed.

Notes

  1. Sample data throughout. Every figure, session, suggestion and check is sample. Nothing calls the API, no key is read and no order is sent; the Design assistant's replies are canned text.
  2. The layout and design are not final. They will be redesigned by Sofi.
  3. The rename is showcase-only for now. The rail PRs still say Labs; the rename to Build is one round of work across the rail, the phone bar and the pictures, and it lands after approval.
  4. Two rows of tabs are intentional for this review. The numbered stepper carries the order and the done ticks; the tab row under it carries the labels at a readable size. They do the same job, so the real designer may merge them into one; both are shown so the team can compare.
  5. Four tools become five stages. The placeholder text on the rail PRs names Design, Backtest, Test Run and Diagnose. Diagnose folds into Improve, and Deploy and Dry Run become stages of their own; the PR placeholder text is to be updated after approval.
  6. One copy detail to settle. The guide's headline says "nine answers" while the form asks ten (market quantity and max positions are asked separately). Say which count to use.

Functionality to build later (after the UI is approved)

  • The Design assistant as a real chat (it is canned sample text today), writing accepted suggestions into the draft.
  • A real backtest engine over historical candles, with fees, slippage and a run you can duplicate with one change.
  • A real dry run against the live book, with fills, latency and a session that ends itself.
  • A real deploy: key checks against the venue, balance reads, limit enforcement and notifications.
  • Improve reading real session history instead of sample numbers, plus the Diagnose tools folded in.
  • Drafts stored per user on the server rather than in the browser session, so they follow the account.
  • Import from Explore into a real catalogue, and the 14 Botcamp agents runnable rather than described.
  • Version history with a diff between v1 and v2, and one-click rollback to a version that was live.
